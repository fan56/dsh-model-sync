### Added

- **`/model-sync migrate-go` — one-shot full opencode-go migration.** One command runs the whole pipeline the old `migrate plan` + `apply` two-step required, per profile: plan (the same `buildMigrationPlanFromDeps` output, never re-implemented), file backups BEFORE any write (`<profileDir>/cordis.patch.yml.bak.<YYYYMMDD-HHMMSS>` with a same-second sequence suffix, plus ONE `~/.dsh/models-store.json.bak.<same-stamp>` for the whole run; 3 newest kept per category by filename timestamp), a SINGLE `ctx.userQuestions` confirmation (local structural `ask({questions, agent, signal})` type, zero new dependencies) whose question names the legacy stubs, the per-id add/move/delete rows (every id deleted via `--adopt`/`--prune-user-extra` listed individually with its kind), the per-profile summary, the plan's managed-after notice quoted verbatim (auto-removal on official delisting), the slots being created and the backup paths — the slots come from the resolved top-level `opencode.go.routes` config (no google slot unless the configuration or an existing section calls for one; no other provider is ever touched), then `applyMigration` with the consent triple computed caller-side (`planHash` + 6-digit `confirmCode` derived via the existing pure helpers, `ackManaged: true`) — `verifyConsent` and the gate are untouched, and `--yes`/`--auto` are unknown flags. After the ask returns the invocation signal is re-checked (abort ⇒ cancel, zero writes; an answer carrying BOTH option labels is treated as ambiguous ⇒ cancel and rerun, never proceed-first). Targets: the current profile by default, or `--all-profiles` = every profile whose `cordis.patch.yml` still carries a legacy opencode-go stub (models-only, no `api`/`baseURL`), discovered through an injectable fs + profiles dir. Non-current profiles are written through a file-backed `SettingsService` over a hand-rolled minimal YAML-subset editor (`src/opencode-go-patch-file.ts`): every op is one original-line-range replacement, the candidate text is re-parsed and compared against a plain-tree simulation of the same op before anything is written, and the PARSE itself refuses every construct the host yaml could load or interpret differently — keys that are not bare plain keys (quoted, whitespace, YAML indicator chars `#*&{[`), duplicate keys in the same mapping, YAML anchors/aliases and merge keys — so such a document is skipped/refused with zero writes instead of silently writing a file the host cannot load; opaque leaves (`!!js`, block scalars) are preserved verbatim outside the edited providers tree but make any op whose target tree contains one refuse; anything else unsupported (tabs, CRLF, multi-line flow) also fails closed with an actionable reason, and a refusing op batch leaves the file byte-identical (all ops complete in memory first). Backups are created under an exclusive O_EXCL claim (same-second collisions retry the next `.N` suffix; atomic tmp+rename, source mode preserved), every file is re-hashed (sha256) right before apply and a file changed since its backup aborts that target (or the whole run for the shared store) with zero writes, and on apply failure every changed file is restored only while its content still matches the post-write sha256 baseline — a file a concurrent process touched is reported as `concurrent modification detected, not restored` with the backup path instead of being clobbered; patch restores go through the same atomic io the apply used and the models-store restore goes through the remote-catalog lock accessor (never a raw overwrite; a store created by the run is removed again under the same guard). Any apply failure stops the batch and reports the failed step, the original error and the restore outcome. On success `opencode.go.enabled` flips to `true` in the current profile through the host settings seam (manual guidance instead of a hard failure when that key cannot be written), and the full detail log lands at `~/.dsh/storages/dsh-model-sync/migrate-go-<stamp>.log` (no credential values, log-write failure only warns). Flags: `--all-profiles`, `--adopt`, `--prune-user-extra`, `--rewrite-refs=default-model|config` (space and `=` forms; all advanced switches default OFF — conservative plan, report-only refs). Missing credential → fail-closed with zero outbound calls and zero writes; missing/unanswered confirmation channel → fail-closed with the manual `migrate plan`/`apply` path and the computed hashes. Design rationale, alternatives, and revocation path: `docs/adr/0001-in-command-single-confirmation-for-migrate-go.md`. +47 checks (`test/opencode-go-one-shot.test.mjs`; reviewer round: parse-time refusals per rule, zero-write on mid-batch refusal, uneditable-target batch strategy, guarded restore + staleness units, abort/blank/ambiguous answers, idempotent second run, second-target failure restore, run-created store removal).

- npm packaged upgrade regression test (pnpm 11 strictDepBuilds, see dsh-subagent-registry#10)

### Fixed

Second review round of the one-shot `migrate-go` path (M1 blocker + minors; every item registered with its file location):

- **Flow collections now decode exactly like the host yaml — or refuse (review M1, blocker).** `parseFlow` in `src/opencode-go-patch-file.ts` used to push every flow item/value through `decodePlainScalar` only, so `fields: {a: "b"}` built the subset tree `{a: '"b"'}`, `input: ["text"]` became `['"text"']`, a flow tag like `{a: !!js x}` silently became text (violating the "tags opaque or refuse" invariant), and a single-pair item `models: [a: b]` became the string `"a: b"` while the host parses `{a: 'b'}` — a conservative keep then wrote the corrupted values back and the host read `['"text"']` while the run reported SUCCESS. Now flow quoted scalars go through the SAME `unquoteYaml` path as block position (single/double quotes, `''`/`\"`/`\\` escapes — verified equal against the host yaml@2 decoder), and flow entries the host would parse differently are REFUSED at parse time with zero writes: tags (`!`/`!!`), single-pair items (`[a: b]`, `[a:, b]`), merge keys, anchors/aliases, empty entries (`[a, , b]` — the host rejects the file) and comments inside the brackets (a `#` there swallows the closing bracket for the host). The flow splitter is now also `\"`-escape-aware (the old splitter closed a double-quoted span at the first `\"`), and a quoted `#` (`["a # b"]`) is content, never stripped.
- **`key: a: b` (colon-space in a value position) is refused at parse (review M2).** The parser accepted this shape while the host yaml rejects the WHOLE document ("Nested mappings are not allowed"); the same check covers a trailing-colon value (`key: a:`) and a mapping indicator on a plain multi-line continuation. A colon NOT followed by space stays plain content (`baseURL: https://…` unaffected).
- **Mapping keys that resolve to null/boolean/number are refused (review M3).** The host yaml folds `true`/`True`/`TRUE`, `null`/`Null`/`~` and `1`/`+1`/`007` into ONE key, so same-level spellings made the host reject the document as duplicate-keyed while this parser saw distinct strings; a single non-string key would still disagree with the parser's string view. Refused outright (block and flow mappings), fail closed.
- **`--rewrite-refs` writes now ride the change tracker (review M4).** The host ref-writer seam was called directly in `src/opencode-go-one-shot.ts`, so its write was invisible to the restore path: a later target's failure left the rewritten references in place, and the stale post-write sha made the guard misreport the file this run had just written as "concurrent modification detected". The seam is wrapped — the write registers on the tracker (restorable on failure) and refreshes the sha baseline immediately.
- **models-store restore is a whole-document BYTE replacement (review M5).** The rollback used to rebuild the store key by key through `writeRaw`, changing key order and applying per-key (non-transactional) while the report and header comments said "byte-restores". The accessor gained `restoreRawDocument` (`src/remote-catalog.ts`): the exact backup bytes staged via tmp + rename under the SAME promise queue + cross-process lock as every other store writer — byte-exact (key order and formatting preserved) and transactional. The report line now says `byte-exact`; the header comment matches the behavior.
- **Failed atomic writes clean their tmp residue; backup claims leave a self-describing placeholder (review M7).** `writeFileExclusive`/`patchIoFor.writeAtomic` in `src/index.ts` now unlink the `.tmp-<pid>-<n>` staging file when the write or rename fails, and the O_EXCL backup claim is stamped with a recognizable placeholder line (`crash residue, NOT a backup (safe to delete)`) so a crash between claim and rename can no longer leave a silent 0-byte `.bak.<stamp>` that looks like a real backup.
- **The confirmation dialog shows what apply will actually write (review M8; still ONE question, TWO options).** Added: `update` rows with the plan's before→after diff of the user-modified profile (report-only rows — apply never overwrites them), the plan's own reason quoted on every per-id action row, the route field values (api/baseURL, compact) on the slot lines, and — the important one — with `--rewrite-refs` in effect, an explicit preview section listing every verified reference rewrite as `surface: before → after` (sessions are always report-only and never appear as rewrite rows).

### Known limitations

Known limitations of the new one-shot `migrate-go` path (registered, not fixed in this round):

- **`isCurrent` matches the current profile by bare name.** In `--all-profiles` discovery (`discoverTargets` in `src/opencode-go-one-shot.ts`) a directory equals the current profile only when its basename equals `currentProfile.key` (or the key is the full dir path). Impact: when the host's profile key is not the profile directory's basename (e.g. `resolveProfileKey` resolved a name that does not match the on-disk directory), the current profile is migrated as a NON-current target — through the file patch editor instead of the host settings seam — leaving the running host's in-memory settings diverging from disk until reload. Trigger: `--all-profiles` with a host whose profile key ≠ profile directory basename. Workaround: run `migrate-go` per profile from inside that profile (single-target mode always treats it as current).
- **`resolveProfileKey` can fall back to a directory path as the store key.** When neither `profileContext.name` nor `DSH_PROFILE` is available, `resolveProfileKey` returns `profile.dir`/`DSH_PROFILE_DIR` (an absolute path), which then prefixes every models-store ledger key (`<profileKey>#<route>#<fp>`). Impact: store slots become path-shaped, so they no longer line up with the name-shaped keys the same profile writes when it later launches with a proper name — migration state/ledger appear fresh and a stale path-shaped slot lingers. Trigger: plugin loaded outside a named dsh profile context (e.g. bare host launch with only `DSH_PROFILE_DIR` set). Workaround: launch inside a named dsh profile.
- **Scalar type domain diverges from the host yaml on non-decimal number forms.** The patch editor's `decodePlainScalar` recognizes integers/decimals only; host yaml@2.8 additionally parses `1e3`, `.inf`/`.nan`, `0x10`, `0o17`, and quoted-escape variants. Impact: a profile patch carrying such forms in fields the migration reads or rewrites gets a plan computed against different types than the host sees (e.g. plugin-side string `'1e3'` vs host-side number `1000`), so a compared/rewritten field can flip representation; untouched lines keep their literal bytes. Trigger: hand-written patch values in scientific/hex/infinity notation inside `llm-pi-ai` providers. Workaround: write plain decimal or quoted strings in the patch.
- **One-shot `migrate-go` does not consume the injected GO_* store seams.** `storesFor` always builds file-backed stores over `modelsStorePath`; the `GO_MIGRATION_STORE_SERVICE` / `GO_OWNERSHIP_STORE_SERVICE` seams that `migrate plan|apply|rollback|status` and the go sync round honor are deliberately not consulted (they cannot express per-profile scoping). Impact: a host or test that swaps the store through those seams will see `migrate-go` read/write the real `models-store.json` instead of the swapped implementation. Trigger: running `migrate-go` in a process that provides alternative store implementations via those seams. Workaround: point `migrate-go` at a scratch store via the `GO_ONESHOT_PATHS_SERVICE` path overrides (what the tests do).
- **Backup claim placeholders can survive a crash and count toward retention.** `writeFileExclusive` stamps the O_EXCL backup claim with a placeholder line immediately after creating it, but a process killed inside the microscopic window between `open(wx)` and the placeholder write still leaves a 0-byte `.bak.<stamp>` file, and any placeholder that does survive matches the backup naming pattern, so `pruneBackups` counts it as a backup (it may evict one real backup more than intended). Impact: cosmetic residue plus a slightly eager retention, never a wrong restore — a placeholder is only ever readable as `record.backup` if a crashed run's name is reused by hand, and its content (empty or the marker line) is obvious to a human. Trigger: SIGKILL inside the claim→rename window. Workaround: delete files containing the marker line (or 0-byte `.bak.*` files) by hand.
- **The flow parser refuses some documents the host yaml would accept.** Two conservative-refusal cases in `parseFlow` (`src/opencode-go-patch-file.ts`): a flow value with brackets inside quotes (`{a: "[x]"}` — the nested-collection pre-check is not quote-aware) and a colon-glued flow key (`{a:b}` — the host parses key `a:b` with a null value, the subset's key matcher refuses the entry shape). Impact: a profile patch carrying such an exotic shape is skipped at discovery / yields no descriptor instead of being migrated; zero writes, fail closed. Trigger: hand-written flow collections of those exact shapes. Workaround: use block style for those entries.

## [0.10.0] - 2026-11-23

本版为 opencode-go 增加 3 条路由的动态同步能力（以官方公开清单为权威源），并提供从手写配置到托管配置的合法迁移与回退路径。措辞取自发布说明草稿；每条已知限制标注依据报告编号。

### Added

- **官方 `/v1/models` 权威源**：以 `GET https://opencode.ai/inference/go/v1/models` 的公开清单为模型来源。无鉴权请求返回 200 条清单（30 个 id），携带凭据时返回收窄后的 11 个 id（entitlement）。凭据仅通过环境变量注入，不打印、不落盘。（依据：交接单「易丢的关键技术事实」、报告 58 §2.7）
- **3 条 opencode-go 路由**：
  - `opencode-go`：chat-completions 协议，承载官方 chat 模型。
  - `opencode-go-msg`：messages 协议，承载 `qwen4-max`；其 baseURL 必须去掉尾部 `/v1`，否则会拼出 `/v1/v1/messages` 导致 404。
  - `opencode-go-resp`：responses 协议，承载 `grok-4.7`。
  （依据：交接单「易丢的关键技术事实」、报告 58 §2.1）
- **`/opencode-status` 只读诊断**：查询当前 profile 的迁移状态与路由写权；只读、零外呼、零写入。（依据：交接单 P0 行、报告 60 B-8）
- **`migrate plan/apply/rollback/status`**：
  - `plan` 为只读，输出逐 id 动作表与迁移后模型清单，不写 settings 或 store。
  - `apply` 受三重显式同意门保护：`planHash`、6 位确认码、`--ack-managed` 知情门；未带 `--ack-managed` 时拒绝并零写。
  - `rollback` 依据整段快照按原键序逐字段还原 settings，清除账本与指纹并收回落权重锁。
  - `status` 查询迁移状态（含 absent / legacy-inherit / legacy-store / foreign-profile / applied 等标签）。
  （依据：交接单 P1d-2 行、报告 58 §2.2、报告 60 B-7）

### Changed

- **`eject go` 已下线**：命令保留为墓碑拒绝（返回 retired 提示、零写、不触发同步轮）。`migrate rollback` 是唯一回退入口。（依据：交接单「用户拍板」、报告 60 B-8）
- **跨进程锁超时改为 fail-closed**：锁只覆盖 models-store（2s 超时）。超时报 `DSH_STORE_LOCK_TIMEOUT`，含锁路径与建议动作；陈旧锁需校验 owner 存活，不盲目破除。旧版「降级继续写」语义已不存在。（依据：报告 35/37 D2/D3、报告 61 §6.2）
- **锁超时与账本失败不再静默**：提供可识别 code，包括 `settings-written-unaccounted`（settings 已写但账本未记，保留锁路径诊断）、`journal-unavailable`（journal 写失败按路由拒绝、零写）、`journal-list-failed`（列举失败）、以及 `journal-descriptor-unavailable`、`ledger-write-failed`、`writer-error`（后两项为最终提交新增）。写入失败路由令命令返回 `kind:'error'`。旧文案 `store NOT modified` / `Retry the operation` 只在零写入路径保留。（依据：报告 53 §6、57 §2.7、60 A-2/A-3、62、63）
- **无宿主 profile 身份时迁移与账本 fail-closed**：拿不到宿主身份时，四个 migrate 入口全部报身份错误，零 settings 写、零外呼、不创建 store 文件，不再塌缩到 `default` 键。（依据：报告 58 §2.6 U2、报告 60 B-7）
- **`go.enabled` 默认仍为 `false`**：保持评审建议的默认关闭，避免开启后冻结现存带 opencode-go 的手写列表；需要同步时显式打开。（依据：交接单「评审建议」）

### Known limitations

12 条，逐条对应报告 61 §6。L12 已于最终提交 `685fab4` 关闭，在限制清单中保留并标注「已修复」。

1. **migrate apply/rollback/restore 的冲突重试复用旧 ops（61 §6.1）**：受 planHash + 6 位确认码 + `--ack-managed` 三重显式同意门保护；但同意之后、写入之前的窄缝内，用户编辑仍可能被已同意的计划覆盖。这与自动同步轮的「冲突即整轮放弃」语义不同，属有意取舍（`mutateWithRetry` 旧 ops 复用有意保留）。影响：极窄窗口内用户编辑可能被计划覆盖。规避：plan 之后、apply/rollback 之前不要编辑相关模型；若已被覆盖，用 `migrate rollback` 回到计划前状态（settings 逐字节还原）。（依据：报告 61 §6.1、§5；报告 62 残余 4）
2. **跨进程锁不保护 `settings.mutate`（61 §6.2）**：锁只覆盖 models-store（2s fail-closed）。settings 已落地后账本失败会留下 journal 供下轮对账；journal 写本身失败（含撞锁）按路由 fail-closed（`journal-unavailable`，零写、下轮重试），不再降级继续 mutate。影响：锁不覆盖 settings 写入本身；撞锁时本轮该路由不写，需下轮重试。规避：看到 `journal-unavailable` 后等待下轮自动重试；不要把跨进程锁当作 settings 写入的保护。（依据：报告 61 §6.2、报告 60 A-3、报告 63）
3. **journal 内容哈希只覆盖 `models` 数组（61 §6.3）**：用户仅改 api/baseURL/apiKeyEnv 时哈希仍相等，对账会补账本；随后 planner 冲突检测会拦截覆盖、要求人工裁决，无静默丢失。另：最终提交把哈希排序改为确定性字节序；若旧版在大小写混排 id 的路由上留下 journal，升级后首轮可能因规则变化判 `journal-stale` 丢弃（方向安全：保留用户值、下轮重规划），典型小写 id 不受影响。影响：身份字段改动不会使 journal 失效，会补账本并可能触发人工裁决；跨版本极端情形可能丢弃旧 journal。规避：改身份字段后跑一次同步并查看冲突提示，按提示人工裁决或 `migrate plan/apply` 重新确认。（依据：报告 61 §6.3、报告 57 §6.1、报告 62 残余 5、报告 63 残余 5）
4. **多路由轮的原子性边界（61 §6.4）**：用户编辑落在路由 A 已写、路由 B 复检之前时，A 保持落地，报表如实列出 already written / discarded，不回滚（S7 口径）。影响：一次同步轮不是跨路由原子；编辑撞在中间会出现部分路由已写。规避：以报表中的 written/discarded 为准；需要一致状态时 `migrate rollback` 后重跑。（依据：报告 61 §6.4、报告 53 S7、报告 57 §2.6、报告 60 B-7）
5. **崩溃窗口验证边界（61 §6.5）**：K1 等中断点以 seam 模拟 + `writeRaw` tmp+rename 原子性论证验证，未做真实 SIGKILL 复现。影响：真实进程被强杀的极端情形未实测。规避：依赖原子写与 journal 对账收敛；强杀后重跑同步让对账完成。（依据：报告 61 §6.5、报告 57 §1/§6、报告 60 遗留 3、报告 62 残余 6）
6. **revision 机制依赖宿主（61 §6.6）**：窗口保护依赖宿主在用户编辑时推进 `llm-pi-ai` revision（真机 dsh 0.2.2-rc.5 已核实）；宿主语义变更时退化为 mutate 后内容哈希一道校验。影响：更换或升级宿主后，若不再推进 revision，保护弱化。规避：宿主升级后复验 fetch 窗口场景，关注 `settings-changed-during-sync` 报表。（依据：报告 61 §6.6、报告 58 §6、报告 60 B-7）
7. **孤儿 journal 无定时清扫（61 §6.7）**：换 Key / profile 改名后产生的孤儿 journal，下次同步遇到即丢弃；migrate apply/rollback 会清本 profile journal。长期不跑同步时 store 有残留槽（无害）。影响：store 中长期残留无用槽。规避：定期跑同步；或执行 migrate apply/rollback 清理本 profile journal。（依据：报告 61 §6.7、报告 57 §6.4、报告 53 C2 实施要点）
8. **公开清单不可用时删除暂停（61 §6.8）**：公开清单无法获取时，未知 id 全部按 unclassified 保守处理（fail-safe），删除功能随之暂停。影响：清单不可达期间，托管模型的自动删除不执行。规避：网络恢复、清单重新可用后重跑同步，删除功能恢复。（依据：报告 61 §6.8、报告 53 方案 D）
9. **多 profile 并发写未真机压测（61 §6.9）**：顺序双 profile 已隔离验证；真实 `~/.dsh/models-store.json` 可能被其他 dsh 进程随时重写（报告 58 观测到一次，非本插件所为）。影响：两个进程同时写同一 store 未做真机并发压测；外部进程可能改写 store。规避：避免并发进程写同一 store；以跨进程锁的 fail-closed 报表为准；外部改写属环境行为。（依据：报告 61 §6.9、报告 58 W2/§6、报告 60）

## [0.3.0] - 2026-09-03

### Fixed

- **Concurrent sync rounds can no longer wipe folded overrides.** `fetchRemoteCatalog` captured the route's pre-fetch snapshot (`stored = await store.read(route)`) and re-attached `overrides: stored?.overrides` into every write path (200 / 304 / 404 / 501 / 503), so an overlapping round whose `persistOverridesToStore` ran between the snapshot read and the write-back was clobbered on the fetch side — the v0.1.5 data-loss shape returning through a new door. The four write paths now call `effectiveStore.update(route, patch)` instead of `write(route, entry)`: the accessor's queue-internal read-modify-write re-reads the route's current entry inside the queue, so the patch only overrides the fields it names and `overrides` (plus any future out-of-band field) survives by construction. The pre-fetch `stored` snapshot stays in scope only for conditional checks (304 ETag match, 4h throttle) and to seed the fall-back models/lastModified/etag values on error paths — it never participates in the write payload. `persistOverridesToStore` similarly moves its read-modify-write into the queue via `updateOverrides(route, overrides)`, so the writer's stage and the fetch's update serialize cleanly and the merge is always based on the latest on-disk state. The `store.read()` path stays strict (corrupt / permission-denied files still surface as errors so the writer can fail closed); only the queue-internal merges tolerate the failure (and rely on the atomic `writeDoc` to heal the corruption on the next successful write).
- **B1: the models-store accessor now seeds every persisted entry to a well-formed shape (no more `{overrides}-only` survivors).** The earlier queue-internal merges used a `{ ...current, ...patch }` spread; an `updateOverrides` stage on an ENOENT / corrupt doc produced an entry of `{overrides: ...}` only — no `models`, no `checkedAt`. The next round's `fetchRemoteCatalog` (when `force=false`) then crashed with a `TypeError` reading `stored.models.length`, the whole sync went unhandled-rejection, and every route after the bad one stopped syncing. v0.2.2 had a fallback path that swallowed the read failure and never saw this; the regression came from the v0.2.3 surface. `update` and `updateOverrides` now use a field-level seed: `models = patch.models ?? current.models ?? []`, `checkedAt = patch.checkedAt ?? current.checkedAt ?? Date.now()`, `lastModified = patch.lastModified ?? current.lastModified ?? 0`, `etag = patch.etag ?? current.etag`, `overrides = patch.overrides ?? current.overrides`. Every persisted entry has the unconditional shape `{ models: RemoteCatalogEntry[], checkedAt: number, lastModified: number, etag?, overrides? }`, so a subsequent read never sees an incomplete shape and the next round's `fetchRemoteCatalog` cannot crash on `stored.models.length`. The seed also never overwrites a value current already holds — a stale pre-fetch snapshot can no longer clobber an out-of-band stage because the patch only writes fields the call site intends to write. `etag: undefined` is still omitted by `JSON.stringify`; the seed falls through to current when the patch leaves a field unset (so 404 / 501 paths now preserve the cached etag instead of clearing it — the next round's conditional request still uses it, harmless if the resource stays gone, useful if it comes back).
- **N1: 304 path patch is now exactly `{ checkedAt }`.** Re-naming `models` / `lastModified` / `etag` on a 304 was unnecessary (304 means "body unchanged" — those fields didn't change), and re-stating them in the patch opened a window for a clobber if a concurrent round had staged one of those fields between the snapshot read and the write-back. The 304 path now passes just `{ checkedAt }`; the seed preserves everything else from the route's current entry.
- **N2: defensive optional chaining on the throttle check.** `stored.models.length` is now `stored.models?.length ?? 0` — the field-level seed always populates `models: []` at minimum, so a missing field here means a legacy entry written before the seed landed; treat it as "no cached entries" rather than crashing.

- **Managed routes with user `modelOverrides` sync again** (the "rejected by settings validation (see log)" incident). The writer folded overrides into the written models but left the `modelOverrides` key in settings — and the dsh llm-pi-ai validation refuses a models list beside non-empty modelOverrides, so every mutate for such routes (notably minimax-cn / xiaomi-token-plan-cn) was rejected atomically and nothing ever landed. The writer now unsets the key in the same mutate as the models write (set+unset apply atomically, so the validation sees models-present + overrides-absent), and — so the v0.1.5 data-loss bug stays dead — stages the raw overrides in `~/.dsh/models-store.json` before the mutate (store-first, so settings is the authoritative source in every failure window: a failed store write skips the mutate entirely and reports `skipped (models-store write failed; settings untouched)`, while a rejected mutate leaves the key in place, where it always wins over the staged copy) and replays them into the target on every later round. Settings overrides win over stored ones (a re-added key is the user's latest intent); routes without overrides take exactly the old code path. Override ids with no matching model in the target are reported on the sync line and kept in the store (they apply again if the id shows up in a later catalog). The report line names the action: `minimax-cn: wrote 25 models (folded user modelOverrides, unset the key)`. Downgrading below 0.2.2 discards folded override values on the next sync under the older version.

- **The builtin catalog snapshot can no longer rot against the host.** `keepBuiltinOnly` emitted ids from a build-time snapshot frozen at 2026-08-28; when pi-ai 0.84.4 removed grok-4.5 from its opencode-go catalog, the 09-01 host upgrade turned the stored bare entry into a dead id that the alpha line's strict llm-pi-ai registration rejects — taking every provider route down with it (the "all providers vanished" incident). `getBuiltinCatalogForRoute` now prefers the host's live pi-ai catalog (discovered via `DSH_CLOSURE_DIR` → `which dsh` → `npm root -g`, mirroring the linker scripts) and falls back to the snapshot only per-route when the host cannot be located. The snapshot itself was regenerated against 0.1.2-alpha.4 (grok-4.5 out, grok-4.6 and the 08-31 pi.dev additions in).

- **Corrupt `~/.dsh/models-store.json` no longer silently clobbers folded overrides.** The store accessor used to swallow every read error (including `SyntaxError` on a half-written file, `EACCES` on a permission-locked store, and `EIO` on storage failure) and return `{}` as if the file did not exist; the writer would then see no stored overrides, accept the raw pi.dev target as the merged view, and overwrite `settings.models` — losing the user's folded `contextWindow` / `reasoningEfforts` / `think` fields on the very next refresh. The store's read path now distinguishes `ENOENT` (a normal first run) from every other failure (which propagate), and the writer short-circuits to reason `store-unavailable` (skip + log + leave `settings.models` untouched) when the read fails AND settings carries no overrides key — `settings.models` is the authoritative fallback in that window. When settings DOES carry the key, settings-wins still proceeds and the new atomic `writeDoc` (tmp + `rename(2)`) heals the corruption on disk as a side effect.

### Changed

- **The plugin rides the dsh RC/stable line; the alpha line is retired.** CI and release workflows install the dsh CLI by resolving the newest of the `latest` (stable) and `next` (rc) dist-tags at runtime — never `@alpha`, never hand-pinned. When a stable 0.1.2+ lands on `latest` it wins over the rc by plain semver compare.
- **dsh host floor `>= 0.1.2-rc.1`.** All peer-dependency floors move from `>=0.1.2-alpha.4` to `>=0.1.2-rc.1`, and the dev closure is pinned exactly at 0.1.2-rc.1.
- CI and release workflows gate on `generate-builtin-snapshot.mjs --check`: a snapshot drifted from the live host catalog now fails the build instead of shipping dead entries.
- The generator script's hardcoded `~/github/dsh-model-sync` project root and `/opt/homebrew/...` pi-ai path are replaced with the same discovery trio — it had never actually run on this machine.

### Test

- Behavior tests (base-less drop, maxTokens keep, keepBuiltinOnly preservation, api-divergent warning) no longer anchor on snapshot membership: they force the precondition via inline builtin data, so catalog drift cannot flip them. New `live-catalog.test.mjs` covers override priority, per-route fallback, and bogus-override fall-through.

### Docs

- README (EN + zh-CN): the support statement now reads "Requires dsh >= 0.1.2-rc.1 — this plugin targets the dsh RC/stable line only (CI and releases resolve the newest of the `latest`/`next` dist-tags at runtime). The alpha line is no longer supported."

## [0.1.6] - 2026-08-31

### Fixed

- **User `modelOverrides` are now durable.** The writer used to fold overrides into the models list and then `unset` the overrides key; the next round regenerated the target from pi.dev, found the stored models different, and silently clobbered the folded fields (think levels, narrowed context windows) after exactly one round. The overrides key is now never written or deleted: each write is target ⊕ overrides, change detection compares against that merged view, and overrides for ids outside the target stay untouched user data instead of being dropped with the key.

### Changed

- `writeMode` now defaults to `settings` (the zero-patch pipeline); `overlay` remains available for the legacy patched-adapter flow.
- Capacity sanity gate (deviation from design doc §3.3 rules 3/5): settings-written capacities override the installed catalog at resolution, and a written `maxTokens` becomes the request-level `defaultMaxTokens` — so listing garbage would trip the "output token limit" family (upstream #1166). A non-positive-integer `contextWindow`/`maxTokens`, or a `maxTokens` not strictly below the context window (listing echoes, e.g. grok-4.6 at 500000/500000), is now skipped with a `DEGRADED` report line instead of written.

### Docs

- README (EN + zh): standalone-distribution statement (the bundled-in-dsh-tui-pi claim is stale), config table aligned with the new defaults, new "Capacity values are upper limits" section with the `modelOverrides` escape hatch.

## [0.1.4] - 2026-08-29

### Fixed

- Register the `/model-sync` command through a `ctx.inject(['commands'], ...)` sub-fiber instead of reading `ctx.commands` inside `apply`. cordis 4 rejects foreign-service property access without a declared inject (`cannot get property "commands" without inject`), so loading the 0.1.3 plugin tree **crashed every dsh boot**. The sub-fiber stays dormant until the host provides the `commands` service, preserving the optional-peer design: hosts without dsh-commands keep auto-sync, and registration fires whenever the registry appears.

## [0.1.3] - 2026-08-28

### Changed

- Default auto-refresh interval `intervalMinutes` 60 → **240 (4h)**. Explicitly configured values are unaffected.
- The `/model-sync` command is registered by the plugin itself through dsh's shared command registry (`@deepseek-ai/dsh-commands`, optional peer) — interactive UIs discover it automatically. (Superseded by the 0.1.4 fix: the original `ctx.commands` read crashed dsh boot.)
